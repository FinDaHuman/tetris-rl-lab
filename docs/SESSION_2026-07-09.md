# Session Log: 2026-07-09

## Night 2 attempt 1 hung at 4.0M steps — diagnosis and fix

The user started Night 2 (Track 3, 100M steps) at 10:21 PM on 2026-07-08.
Console output stopped after iteration 976 (3,997,696 steps, ~10:40 PM);
by 1 PM the next day the process was still running at full CPU (~8 cores,
424k CPU-seconds) with no new output in log.txt, progress.csv, TensorBoard,
checkpoints, or eval files.

### Diagnosis

A py-spy stack dump of the live process (PID 7384) showed the main thread
inside `EvalCallback._on_step → evaluate_policy → model.predict` — the
eval scheduled at exactly 4.0M steps (eval_freq 1M; the 1M/2M/3M evals had
completed, `evaluations.npz` timesteps `[1000000, 2000000, 3000000]`).

Root cause: an eval episode that can never terminate.

- The env ends an episode only on top-out (terminated) or after
  `max_pieces` locks (truncated). Both require pieces to lock.
- Gravity moves the piece down 1 row on every non-drop action, so episodes
  looked bounded — but the SRS kick tables contain upward kicks (drow −1
  and −2). A rotation that needs an upward kick lifts the piece 1–2 rows
  while gravity pulls it down only 1.
- `EvalCallback` runs `deterministic=True`. A deterministic policy in a
  deterministic env that revisits a state repeats forever: rotate with an
  upward kick, gravity down, same state, same observation, same action.
  Training never hangs because actions are sampled stochastically; the
  4M-step policy was the first whose argmax behavior hit such a cycle.

### Fix

`TetrisScoreEnv` now has `max_steps_per_piece` (default 50). If a piece
survives 50 consecutive non-locking steps, the env force-locks it with a
hard drop inside the same `step()` — the same idea as real Tetris'
move-limit lock delay, which exists precisely to prevent infinite spins.
Every episode is now bounded by `max_pieces × (max_steps_per_piece + 1)`
steps. Force-locking (rather than truncating the episode) also avoids a
reward exploit: truncation would have let a policy hover to dodge the
top-out penalty.

Legit play is unaffected: a piece needs at most ~21 gravity steps to reach
the floor, so a 50-step budget only triggers on degenerate hovering. Reward
accounting is unchanged in lines mode (computed from state deltas across
the whole step, including the forced drop) and in score mode the forced
drop's engine reward is added in.

Tests: `test_forced_lock_bounds_steps_per_piece` and
`test_every_constant_action_policy_terminates_within_bound` added in
`tests/test_custom_env.py`; suite is 19 passed. A 16k-step train with two
eval callbacks completed end-to-end after the fix.

This also protects the standalone `evaluate --deterministic` commands in
the plan (steps 2.2/2.3), which had the same infinite-episode exposure.

### What the training curve says

- Eval mean reward climbed steadily from −4 (start) to ~+7 by **36M steps**,
  then **plateaued**: from 36M to 100M it oscillated between ~0 and ~7 with
  no upward trend. The extra 64M steps bought essentially nothing.
- PPO update diagnostics were hot for the *entire* run: `approx_kl`
  ~0.15–0.18 and `clip_fraction` ~0.41–0.44 (healthy is roughly ≤0.03 and
  ≤0.2). Attempt 1's early readings were not a transient — every policy
  update overshoots the trust region, which is the textbook cause of
  exactly this plateau-then-oscillate shape.
- Behavior: the agent clears ~1 line then tops out after ~28 pieces of the
  500-piece cap. Survival is now the bottleneck, not discovering line
  clears.

### Decision: Night 3 = same run at lr 1e-4

Per the one-change-at-a-time rule, the single evidence-backed lever is
`--learning-rate 0.0001` (was 3e-4): the sustained hot `approx_kl` /
`clip_fraction` plus the 36M plateau point directly at oversized updates.
The other levers (line_reward 50, longer max-pieces, entropy schedule)
address reward-signal problems the run no longer has — the agent finds
lines; it fails to *refine*. A fresh run (the trainer has no resume flag)
with the same seed keeps the curves directly comparable. Command and
decision gate (promote only if mean_lines beats 1.04) are in
`TRAINING_PLAN.md` under "Night 3". The optional Track 1 attempt moved to
Night 4.
